# Production-site replicas (`lite/sites/<site>/`)

Each production Islandora Lite site runs next to the Lite dev site inside this one Compose
project: its own `drupal-<site>` container (image FROM the Lite image + the site's
`config/sync`, themes and site files) and its own `db-<site>` on `mysql:8.0`, sharing
Solr, Blazegraph, Cantaloupe, FITS and Traefik. Served at `http://<site>.islandora.io`.
Design and rationale: `LOCALIZE.md` at the repo root.

## One local folder per site

`lite/sites/*` is git-ignored here except `_template/` and this file. A site folder is a
local working folder scaffolded by `make site-add`; it is not versioned anywhere.

| Path | Provided by |
| --- | --- |
| `site.env` | `make site-add`, then edited |
| `docker-compose.yml` | rendered from `site.env` (`make site-render`) |
| `site-files/` | you: small public files named in config (theme logo, ...) |
| `NOTES.md` | intake appends its assess report |
| `repo/` | you: `git clone <internal GitHub> repo` (the site's composer project) |
| `themes/<name>/` | you: each theme in `SITE_THEMES` (private GitHub) |
| `db/` | you: the handover (`*.sql`, `*.sql.gz`, `*.sql.xz`, or `*.tar.gz`/`*.tgz` of `.ibd` files); intake writes `db/<site>.sql.xz` and moves your file to `db/incoming/` |
| `solr/conf/` | you, optional: the production Solr core's `conf/` folder, copied as is (intake adapts it to this stack's Solr) |
| `stage/`, `db-raw/` | generated by intake |

## Workflow

```bash
# new site
make site-add SITE=memory              # scaffold lite/sites/memory/ ; edit site.env ; make site-render SITE=memory

# your manual inputs
git clone <internal repo> lite/sites/memory/repo               # or set SITE_CODE_DIR in site.env
git clone <theme repo> lite/sites/memory/themes/dsu_subtheme_barrioDepartments
cp <handover file> lite/sites/memory/db/

# optional (skip either one: nothing fails, the defaults apply)
cp -R <production Solr core conf/ folder> lite/sites/memory/solr/conf   # else: config generated by search_api_solr
cp -R <production Cantaloupe config folder>/. lite/cantaloupe/conf/       # else: the image's config; once for the stack (lite/cantaloupe/README.md)

# validate the manual inputs (read-only; repeat until it prints "Ready for intake")
make site-check  SITE=memory

# run: intake (verify + stage code, themes, Solr and Cantaloupe config, normalize the database, NOTES.md), build the
# drupal-memory image, then start it (first start localizes: re-point services, Solr core,
# facets, updb, placeholders). Separately: site-intake, site-build, site-up.
make site-deploy SITE=memory
make site-login  SITE=memory
```

Everyday: `make sites`, `make site-drush SITE=memory CMD="status"`, `make site-shell`,
`make site-finalize` (re-run the localization), `make site-solr-conf` (swap the site's
`solr/conf` into the existing core, then reindex), `make site-placeholders`
(`MODE=relink|per-file`), `make site-users-from-lite` (handovers without account tables),
`make site-dump DEST=...`, `make site-down`, `make site-disable`, `make site-reset`
(destructive for that site only: containers, volumes, image, stage, normalized dump).

Plain `make up` / `make down` include enabled sites (they are in `COMPOSE_FILE` and
`COMPOSE_PROFILES` of `.env`). `make clean` (upstream, destructive) removes site volumes too.

## Accounts: never the production ones

A handover database may contain the account tables (and their password hashes). They are
never used: `normalize-dump.sh` drops the rows of `users`, `users_field_data`, `users_data`,
`user__roles`, `user__user_picture`, `shortcut_set_users`, `sessions` and `flood` from
every normalized dump, the `.ibd` recovery never attaches those tablespaces (default
`SKIP_TABLES`), and the first start copies the accounts of the Lite dev site in
(`lite-accounts-from-lite.sh`), so uid 1 is `admin` with the stack password
`secrets/DRUPAL_DEFAULT_ACCOUNT_PASSWORD`. `make site-users-from-lite SITE=<site>` repeats
that on demand; `make site-dump` writes dumps through the same filter.

## What the first start does (`lite/site-image/rootfs/etc/s6-overlay/scripts/install.sh`)

The MySQL container seeds the database from `db/<site>.sql.xz` on its first start. Drupal
then runs `lite-site-finalize.sh` once (state key `lite.localized`): re-point Solr, IIIF,
FITS, Mirador, advancedqueue and ffmpeg at this stack (`lite-hydrate.sh`), JWT key, Solr
core (`SITE_SOLR_CORE`, shared `dsu_multisite` by default; created from the site's
`solr/conf` if provided, see "Solr layout"), delete facets whose field no
longer exists, `drush updb`, accounts from the Lite site with uid 1's password set to
`secrets/DRUPAL_DEFAULT_ACCOUNT_PASSWORD`, copy `site-files/`, then media placeholders. Files are never part of a handover:
`relink-media-placeholders.php` generates one generic file per (scheme, MIME type) under
`<scheme>://lite-placeholders/<slug>.<ext>` and rewrites every `file_managed.uri` to its own
path `<scheme>://lite-placeholders/<slug>/<fid div 1000>/<fid>.<ext>`, a symlink to the
generic file (one path per file row, because Drupal's private download handler checks
access on the first row that matches a URI; originals in table `lite_file_uri_backup`).
`ensure-referenced-files.php` then creates generic files for paths that are not managed
files: `public://` names in config (theme logo) and `/sites/default/files/...` links in
text fields (inline images). No `drush cim`, no reindex (run
`make site-drush SITE=<site> CMD="search-api:index"` when you want).

Themes are staged at `web/themes/<name>/` (content and prod paths such as
`/themes/<name>/images/...` keep working).

## Solr layout

`SITE_SOLR_CORE=dsu_multisite` (default) mirrors prod: every site indexes into one shared
core, mounted once on `solr` by `docker-compose.lite.yml`. `SITE_SOLR_CORE=<site>` gives a
site its own core (volume `solr-core-<site>`, added to `solr` by the site's compose file).
The exported config may name another core; `settings.lite.php` overrides it at runtime.

The first site to start creates the core: from its `solr/conf/` (the production core's
`conf/` folder, adapted to the Solr 10 of `islandora/solr` and test-loaded by intake, see
LOCALIZE.md §5) when it has one, otherwise from the config search_api_solr generates. An
existing core keeps its config until `make site-solr-conf SITE=<site>` swaps in that site's
(the old one stays in the core directory as `conf.bak-<timestamp>`; a failed RELOAD
restores it); then reindex every site that uses the core. To take a newer production
config: replace `solr/conf/`, `make site-deploy SITE=<site>`, then `make site-solr-conf SITE=<site>`.
